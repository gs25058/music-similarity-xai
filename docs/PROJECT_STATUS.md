# 프로젝트 현황과 지금까지 알게 된 점

기준일: **2026-11-05, Asia/Seoul**. 저장소의 코드, 로컬 JSON 보고서, 테스트 로그와 [실행 검증 기록](VALIDATION.md)을 대조해 작성한 현황이다. 이후 작업 시 이 문서의 기준일과 검증 결과를 함께 갱신한다.

이 문서는 초기 MVP 단계의 현황이다. 이후 추가한 시간순 근거·주장 검증·Qwen LoRA·선택적 soft token과 실제 실험 결과는 [Qwen 확장 안내](QWEN_ALIGNMENT.md) 및 [최신 검증 기록](VALIDATION.md)에 정리했다. 아래의 고정 Qwen 설명은 기본 경로에 해당한다.

## 1. 현재 어디까지 왔는가

**합성 WAV 두 개를 입력해 구간 비교, 학습 체크포인트 추론, SongFormer 구조 분석, 로컬 Qwen 판단, JSON 보고서 생성까지 실행 가능한 MVP가 구현됐다.** 공개 모델 연결과 작은 학습·저장·재로딩도 확인했다. 전체 코퍼스 본 학습과 실제 음악에서의 성능 검증은 아직 수행하지 않았다.

현재 가장 중요한 문제는 **작은 학습 모델의 높은 오탐률과 Qwen 설명의 충실도**다. 프로그램이 실행되고 응답 형식이 맞는다는 사실만으로 음악적 판단이 정확하다고 볼 수 없다.

| 항목 | 현재 상태 | 확인 범위와 남은 점 |
| --- | --- | --- |
| 저장소 연결 | 완료 | `origin`: `https://github.com/gs25058/music-similarity-xai.git`, 작업 폴더 `/src/gs25058/AI_project`, 브랜치 `main`. |

## 2. 합의된 범위와 현재 시스템

판단 대상은 **추가 검토에 필요한 음악적 유사성**이다. 두 곡의 전체 음원에서 어느 구간이 어떤 음악 요소로 대응하는지 보여주는 것이 목적이다.

- 소스 코드는 사용자 요청에 따라 `src/`에 둔다. CLI는 저장소 루트에서 `python -m src`로 실행한다.
- 공식 모델의 크기를 유지한다. DSP 경로는 외부 가중치가 없는 환경에서 실행할 별도의 기준 경로다.
- 분석 요소는 음정 진행, 리듬, 화성, 반주·베이스, 프레이즈·곡 구조다. 지원하지 않는 정보는 `unavailable`로 표시한다.
- `reference_files/`는 선행연구 원문·정리 자료의 로컬 보관 폴더이며 Git에서 제외한다.
- 데이터·가중치·캐시·체크포인트·실험 결과도 Git에서 제외한다. 코드 출처와 모델·데이터 버전은 별도 문서로 보존한다.

```text
두 곡의 전체 음원
  → analyze_song: 리샘플링, 창별 특징, 전체 곡 구조 분석
  → compare_songs: 모든 창 쌍의 요소별 코사인, 대응 후보 구성
  → 근거 ID, 양쪽 시간, 점수, 음악 정보와 누락 상태, 구조 맥락
  → judge_pair: 규칙 기준선과 고정 Qwen의 판단, 응답 검증
  → 원본 근거의 시간·점수를 보존한 JSON 보고서
```

시간 순서가 이어지는 창을 연결한 후보와 가장 강한 개별 창을 함께 보존한다. 긴 연결 후보만 남기면 정확한 삽입 위치가 넓은 구간에 가려지는 문제가 있었기 때문이다. 보고서의 인용 시간은 LLM이 새로 작성한 값을 사용하지 않고 원본 근거에서 가져온다.

## 3. 모델별 역할과 해석 범위

| 구성 | 사용하는 모델·방식 | 해석할 때 지켜야 할 범위 |
| --- | --- | --- |
| DSP | 음고 에너지·온셋·크로마·저음 특징 | 혼합 음원에서 계산한 프록시다. 분리된 주선율, 실제 베이스 연주, 검증된 코드로 해석할 수 없다. |
| MERIT | MERT-v1-330M + 공식 선율·리듬·음색 헤드 | 음색은 반주·베이스가 아니다. 화성·프레이즈 구조는 이 헤드들이 지원하지 않는다. |
| 우리 모델 | MERT-v1-95M + 네 시간축 헤드 | 각 헤드가 음악 정보 예측과 비교 임베딩을 함께 출력한다. 보고서의 예측 정보는 검증된 정답과 구분한다. |
| SongFormer | 공식 전체 곡 추론 | verse·chorus 등 기능 라벨은 맥락이다. 양쪽이 같은 후렴이라는 이유로 유사도 점수를 가산하지 않는다. |
| Qwen | **Qwen/Qwen3.5-0.8B**, 고정 가중치 | 음원 대신 구조화된 근거를 받아 판단과 한국어 설명을 생성한다. 자체 음악 인식 모델로 사용하지 않는다. |

우리 모델의 네 헤드는 다음 정보를 예측한다. 없는 정답과 패딩은 손실에서 마스킹한다.

| 헤드 | 음악 정보 예측 | 별도로 학습하는 출력 |
| --- | --- | --- |
| 음정 진행 | 주선율 음고·음 시작점 | 음정 진행 비교 임베딩 |
| 리듬 | 박 위치·음 시작 패턴 | 리듬 비교 임베딩 |
| 화성 | 시간별 크로마, 정답이 있는 코드 근음·종류 | 화성 비교 임베딩 |
| 반주·베이스 | 반주 또는 베이스의 음고·음 시작점 | 반주·베이스 비교 임베딩 |

손실은 **음악 정보 예측 손실 + 요소별 쌍 유사도 손실**이다. 예측 손실을 끈 ablation도 같은 백본·데이터·seed로 실행할 수 있다. 해당 ablation의 학습하지 않은 음악 정보 예측은 `unavailable`로 표시한다.

**코드 구조상 해석:** 현재 모델은 음악 정보 예측을 보조 과제로 함께 학습하는 요소별 임베딩 모델이다. 최종 비교가 예측 개념 값만을 통과하는 엄격한 Concept Bottleneck Model은 아니다. 비교 임베딩이 별도로 존재하므로, 개념 값을 바꾸면 최종 판단도 그에 따라 바뀐다는 주장은 아직 할 수 없다. 선행연구의 개념 개입 실험을 적용하려면 추가 설계와 검증이 필요하다.

## 4. GPU와 실행 환경에서 알게 된 점

처음 기본 샌드박스에서 GPU가 보이지 않아 CPU 환경으로 판단했지만, 이후 **권한 확장 실행에서 NVIDIA RTX A6000 48GB와 CUDA 연산을 확인했다.** GPU가 호스트에 없는 상황과 실행 환경에서 장치가 가려진 상황을 구분해야 한다.

GPU에서 MERT 헤드 학습·부분 미세조정, 체크포인트 추론, SongFormer, Qwen을 실행했다. 최근 검증은 `CUDA_VISIBLE_DEVICES=1`로 물리 GPU를 선택했고 프로세스 내부에서는 `cuda:0`으로 표시됐다. GPU 번호는 실행 예시이며, 다음 실행 때 해당 장치가 비어 있다는 보장은 아니다.

| 환경 | 역할 | 기록된 주요 버전 |
| --- | --- | --- |
| `.venv` | 핵심 파이프라인·MERT·MERIT·학습 | PyTorch 2.6.0+cu124, Transformers 4.38.2 |
| `.venv-clean` | 외부 모델 없이 독립 설치·CPU 검증 | PyTorch 2.6.0+cpu, Transformers 미설치 |
| `.venv-songformer` | SongFormer worker | PyTorch 2.4.0+cu124, Transformers 4.51.1 |
| `.venv-qwen` | Qwen worker·제약 디코딩 | PyTorch 2.6.0+cu124, Transformers 5.20.2, LMFE 0.11.3 |

모델별 의존성 충돌을 피하려고 별도 Python 프로세스와 JSON으로 통신한다. 모델 구조·파라미터 수를 축소하지 않았다. Qwen은 CPU float32, GPU bfloat16으로 실행하며 양자화하지 않았다. 환경 전체 버전과 과거 CPU 기준 버전은 [environment_versions.json](environment_versions.json)에 있다.

GPU 미세조정 중 선형 보간 역전파의 비결정적 연산 경고가 있었다. seed와 설정은 기록하지만 GPU 실행의 비트 단위 일치를 보장하지 않는다.

## 5. Qwen에서 알게 된 점

### 현재 설정과 non-thinking의 이유

현재 모델은 **Qwen3.5-0.8B**다. 가중치를 고정하고 `enable_thinking=False`, greedy 생성으로 실행한다. 상위 근거 최대 세 개의 ID·양쪽 시간·요소 점수·예측 음악 정보·누락 상태·구조 맥락을 전달한다. 긴 음악 정보는 온셋 개수, 상위 크로마 클래스, 최빈 예측 클래스 등으로 요약하고 원본은 보고서에 보존한다.

non-thinking은 이미 계산된 근거를 짧은 판단과 설명으로 정리하는 역할, 출력 길이와 실행 비용을 고려한 선택이다. **thinking보다 정확하다는 실험 결과는 없으며, GPU를 사용할 수 없어서 강제한 설정도 아니다.** 같은 근거로 thinking/non-thinking을 비교하는 실험은 아직 하지 않았다.

### 실제로 겪은 문제와 반영한 조치

| 관찰한 문제 | 현재 반영한 조치 | 남은 한계 |
| --- | --- | --- |
| 시간을 합쳐 쓰거나 점수를 과장해 서술 | 설명에서 숫자를 제한하고 시간·점수는 원본 근거에서 표시 | 질적인 과장이나 잘못된 해석까지 막지는 못한다. |
| 반복 문장, 한국어가 아닌 출력 | 한국어 비율·반복 검사, 설명 안에서만 네 토큰 반복 제한 | 자연스럽고 일관된 음악적 설명까지 보장하지 않는다. |
| 광범위한 정규식 제약의 느린 토큰 탐색 | JSON 자유 문자열 캐시 재사용 | 고정한 라이브러리의 캐시 API에 의존하므로 버전 변경 시 회귀 검사가 필요하다. |
| 캐시와 문자 parser의 허용 범위 차이로 JSON이 중간에 끊김 | 한글·영문·구두점의 허용 범위를 맞춤 | 임의의 다른 언어·유니코드 문장을 지원하는 디코더는 아니다. |
| 불완전 UTF-8 토큰 조합으로 문자 제한 우회 | 설명 캐시에서 해당 토큰 제외 | 모델의 자유로운 토큰 선택을 제한하는 방식이므로 형식 통과율을 무제약 생성 능력으로 해석할 수 없다. |
| Transformers v5와 LMFE의 import 경로 차이 | 공개 클래스에 런타임 호환 별칭 제공 | 설치 버전을 바꿀 때 재확인이 필요하다. |

근거 ID는 별도의 enum으로 제한하므로 `E001` 등의 숫자는 유지된다. 응답은 허용된 판단 라벨·필수 필드·중복 및 알려지지 않은 ID 등을 검사한다. 실패하면 최대 한 번 재요청하고, 다시 실패하면 `failed_rule_fallback`으로 규칙 결과를 사용한다. 평가에서 이 fallback을 Qwen 성공으로 세지 않는다.

**가장 중요한 관찰:** 최종 GPU 통합 응답은 JSON과 ID 검사를 통과했지만, 높은 유사성을 판단하면서 설명 끝에서는 그 판단 기준이 충족되지 않았다고 서술했다. `executed_validated`는 응답 형식과 근거 ID 검증 상태다. 설명 충실도나 음악적 판단 정확도를 의미하지 않는다.

선택적 `causal_conv1d`와 `flash-linear-attention` 커널은 설치하지 않았고 참조 구현으로 실행했다. 통합 보고서의 Qwen 단계는 약 **117.448초**였다. 모델 로드 8.443초, 토크나이저 캐시 9.590초, 생성 99.415초이며 MERT/SongFormer 시간은 포함하지 않는다. 빠른 커널 적용 효과는 아직 측정하지 않았다.

## 6. 데이터와 학습에서 알게 된 점

- **원곡 ID로 먼저 분할해야 한다.** 구간이나 변형을 먼저 만든 뒤 분할하면 같은 원곡이 학습과 평가에 섞일 수 있다. 현재 manifest 누출 검사가 있다.
- **음악 변형은 여러 요소를 동시에 바꿀 수 있다.** 절대 크로마가 달라지는 조옮김 등 의미가 불확실한 라벨은 `null`로 마스킹한다. 음성 쌍은 여기서 negative pair를 뜻한다.
- **POP909의 `BRIDGE`는 보조 선율 트랙이다.** 곡 구조의 bridge나 verse/chorus 정답으로 사용하지 않는다. `MELODY`는 주선율, `PIANO`는 반주로 처리한다.
- **피아노 반주의 저음과 실제 베이스 연주 정답은 다르다.** `piano_accompaniment_low_register_derived`와 `actual_bass_midi`로 출처를 구분한다.
- **실제 데이터에는 정답이 없는 구간이 있다.** POP909 첫 구간의 주선율이 비어 있으면 손실과 정보 출력을 마스킹한다. 학습하지 않은 헤드를 근거처럼 표시하지 않는다.
- **Slakh redux는 단순한 split별 ID 목록이 아니다.** 공식 action-map의 omit/move를 적용하고 UUID 중복을 검사한다.
- **BabySlakh의 metadata flag와 실제 파일이 달랐다.** 파일이 존재하는데 saved/rendered가 false인 사례를 발견했고 실제 파일을 읽되 불일치를 기록한다.
- **현재 실제 데이터 학습은 통제 MIDI 재렌더링이다.** Slakh mix·stem을 읽는 로더는 있지만 원래 스템 녹음 조건의 학습·평가를 완료한 것은 아니다.

합성 데이터는 원곡 12개를 train 8 / validation 2 / test 2로 나눈 뒤 변형 쌍 60개와 삽입 사례 세 개를 만든다. test에는 쌍 10개, 화성의 유효 라벨 쌍은 8개, 삽입 사례는 한 개뿐이다.

실제 자료 검증에서는 POP909 세 곡, BabySlakh `Track00020` 한 곡을 사용했다. Slakh 샘플에서 베이스 음표 336개, 악기 스템 10개, 약 347.754초의 베이스 음원을 확인했다. 이 한 곡으로 새로운 validation/test를 만들지는 않았다.

MERT의 예전 weight norm 직렬화 키를 현재 이름으로 연결하고 누락·추가 가중치를 검사했다. GPU 미세조정에서 발생한 span masking 문제에는 downstream 설정의 `apply_spec_augment=False`를 적용했다. 모델의 사전학습용 마스킹을 정답이 있는 음악 정보 학습에 그대로 적용하지 않도록 한 조치다.

## 7. 직접 확인한 결과와 해석

| 검증 | 실제 결과 | 이 결과로 주장할 수 있는 범위 |
| --- | --- | --- |
| 독립 CPU 환경 테스트 | 기본 12개 통과, 선택 의존성 테스트 5개 건너뜀 | 핵심 처리·마스킹·누출·근거 검증 등의 회귀 확인 |
| 별도 Qwen 환경 테스트 | 실제 토크나이저로 디코더 테스트 5개 통과 | 가중치 추론 없이 형식·문자·ID 제약 경로 확인 |
| 오프라인 smoke | 합성 생성 → 학습 → 체크포인트 → WAV 추론 → JSON 평가 성공 | 새 환경에서 외부 가중치 없이 실행 가능한 경로 확인 |
| GPU 헤드 학습 | train/validation 8/8쌍, 2 epoch, 마지막 손실 1.3061/1.3952 | 최적화와 저장·재로딩의 동작 확인 |
| GPU 마지막 두 블록 미세조정 | 2/2쌍, 1 epoch, 마지막 손실 1.0526/1.1195 | 부분 미세조정 경로 확인 |
| 백본 파라미터 감사 | CPU 미세조정 체크포인트에서 10·11번 블록의 32개 텐서만 변경 | 실제로 지정한 블록만 바뀌는지 확인 |
| 합성 삽입 위치 | 최상위 대응 A 10–20초 / B 15–25초, 양쪽 최소 IoU 1.0 | 동일 WAV 패턴을 복사한 test 사례 한 개의 위치 검출 |
| SongFormer | 양쪽 전체 곡에서 기능 라벨·경계 반환 | 추론 연결 확인. 구조 정답 정확도는 미평가 |
| 최종 통합 Qwen | 첫 응답의 JSON/ID 검사 통과, `high_similarity` | 연결·형식 확인. 수동 검토에서 설명의 모순 관찰 |
| Qwen A/B 교환 | 한 사례의 응답 2/2 형식·ID 통과, 판단 1/1·ID 집합 1/1 일치 | DSP의 동일 근거를 교환한 작은 일관성 검사 |

합성 test에서 예측 손실을 포함한 MERT 95M 모델의 AUC는 음정 0.875, 리듬 1.000, 화성 1.000, 반주·베이스 0.875였다. 그러나 기본 임계값 **0.8**에서 어려운 음성 쌍의 음정 오탐률은 **1.0**이었다. 점수를 순서대로 구분하는 능력과 실제 판단 임계값의 적합성은 별도로 평가해야 한다. 표본도 작아 실제 음악 성능을 추정하기 어렵다.

MERIT 선율과 우리 모델의 음정 진행은 동일 과제가 아니다. 엄밀한 공통 비교 요소는 리듬이며, MERIT 음색을 반주·베이스와 비교하지 않는다. 예측 손실 포함/제외 모델은 손실 항 자체가 달라 전체 손실의 크기만으로 우열을 판단할 수 없다.

Qwen A/B 평가는 **같은 후보·근거를 유지하고 양쪽 시간·음악 정보·맥락을 교환한 검사**다. 두 음원을 바꿔 전체 파이프라인을 다시 실행해도 후보 선택까지 대칭이라는 의미는 아니다. 근거 제거·변경과 사람에 의한 설명 충실도 평가는 아직 남아 있다.

전체 수치, 과거 CPU 기준선과 공개 녹음 실행 내역은 [VALIDATION.md](VALIDATION.md)에 있다. 공개 녹음 예제는 같은 녹음의 겹치는 발췌이며 독립된 두 곡의 평가와 구분한다.

## 9. 다음 작업의 우선순위

1. **데이터와 평가 범위 확대.** 원곡 분할을 유지하며 실제 자료와 어려운 음성 쌍을 늘린다. 주선율·코드·베이스 정답의 가용성과 변형별 라벨을 점검하고, 임계값 선택은 validation에서 수행한다.
2. **본 학습과 공정한 ablation.** 같은 데이터·백본·seed·학습량으로 예측 손실 포함/제외 모델을 비교한다. 마지막 두 블록 미세조정은 별도로 평가한다. 작은 smoke 손실을 연구 성능으로 사용하지 않는다.
3. **Qwen 설명 충실도 평가.** 여러 긍정·음성·근거 부족 사례를 준비하고 근거 제거·변경, A/B 교환, 입력에 없는 주장, 판단과 설명의 모순을 측정한다. 규칙 결과와 같은 근거로 비교하고 사람 평가를 추가한다.
4. **구조 분석 평가.** 실제 구간 주석으로 SongFormer 경계·기능 정확도를 확인한다. 세밀한 프레이즈 유사성을 추가하기 전에는 현재의 `unavailable` 상태를 유지한다.
5. **실행 시간 개선 검토.** 모델 로드·토크나이저 준비·생성을 분리해 측정한다. 선택적 GPU 커널과 worker 재사용은 별도 검증 후 적용한다. 현재의 고정 모델 크기는 유지한다.

다음 명령은 저장소 루트에서 실행한다. 설치와 모델 준비는 [README](../README.md)에 따른다.

```bash
# 외부 가중치 없는 전체 smoke 실행
PYTHON=.venv-clean/bin/python bash scripts/run_smoke.sh

# 현재 합성 데이터·GPU 학습 체크포인트로 전체 통합 실행
CUDA_VISIBLE_DEVICES=1 .venv/bin/python -m src compare \
  data/synthetic/insertion/test/song_a.wav data/synthetic/insertion/test/song_b.wav \
  --backend ours --checkpoint checkpoints/gpu/mert95_smoke.pt \
  --songformer-python .venv-songformer/bin/python --judge qwen \
  --qwen-python .venv-qwen/bin/python --device cuda --out results/integrated.json

# 실제 데이터 준비 후 별도로 실행하는 본 학습. 아직 실행하지 않았다.
PYTHON=.venv/bin/python DEVICE=cuda EPOCHS=30 \
  bash scripts/train_full.sh data/prepared/manifest.json
```

이 현황 문서는 새 실험을 실행한 보고서가 아니다. 기존 코드·산출물·로그를 확인해 현재 상태와 다음 판단에 필요한 정보를 정리한 문서다.
